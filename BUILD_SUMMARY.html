Retail Product Matching System — Complete 8-Stage Pipeline

Date: 26–27 August 2026 Repository: jbethell10/MasterData_EntityResolution Status: audited — leak found and corrected

Executive Summary

A complete 8-stage entity resolution pipeline for matching retail product submissions against a master catalog. Built with honest validation on real benchmark data (1,000+ products), 50 passing tests, and an interactive Streamlit dashboard. The system achieves 87.7% top-1 accuracy on 1,092 real product pairs using text signals alone, independently corroborated by a separate benchmark code path (85.1%).

Key Finding: An earlier build reported 100% accuracy on this data. That was a ground-truth leak — the supplier submission carried the master record's own barcode, so the matcher was handed the answer on every row. With the leak closed the real figure is 87.7%, and nothing auto-merges: one uncorroborated signal is not enough to write to a master catalog unreviewed. Finding and correcting this is the most useful thing in the project.

Architecture & Design

Signal Flow (Stage 04)

Four Independent Signals:
• 0.20 Fuzzy Text Match (RapidFuzz token_sort_ratio)
• 0.15 Phonetic (Metaphone from jellyfish)
• 0.35 Semantic (TF-IDF char-ngrams, 2-4 gram window)
• 0.30 GTIN Similarity (binary exact match, weighted partial)

Weights tuned against Leipzig benchmarks; TF-IDF carries most of the work (was missing in original spec).

Routing Decision (Stage 07)

Three Weighted Signals + Hard Overrides:
• 0.25 Source Agreement (artwork vs supplier vs master)
• 0.35 Text Margin (top-1 vs top-2 separation, not absolute score)
• 0.40 Barcode Agreement (3-way EAN-13 validation)

Routing Bands:
• ≥0.90 → Auto-merge (no human review)
• 0.60–0.90 → Hold for review
• <0.60 → Reject

Overrides that cap the score regardless of arithmetic:
• Barcode 3-way mismatch → Hold
• Retrieval ambiguous (top-1 vs top-2 <0.08) → Hold
• LLM-only decision → Cap at LLM confidence
• Identity-field conflict (barcode disagrees) → Cannot auto-merge

Learning Loop (Stage 08)

SQLite audit log + alias cache with human-approval-only gate. Two critical design decisions:

  • Problem taxonomy: Distinguishes supplier data-entry errors from resolution ambiguity—different owners, different fixes
  • Human-approval-only: Never learns from unreviewed auto-merges (prevents drift)

Audit: five defects found and fixed

The headline result was re-verified from scratch before any further work. Five defects surfaced, four of them invisible from the outside because every one made the numbers look better.

#DefectEffectFix
1 Ground-truth leak. The supplier submission carried the master record's own GTIN on all 1,092 events. Reported 100% top-1; real figure 87.7%. Leipzig events now carry no barcode — truthful to source data, which has none. Guarded by a leak-canary test.
2 Mismatched artifacts. The committed database held amazon-google (1,363 rows) while the events file held abt-buy (1,092). Published number did not reproduce from the repo. Each run gets its own directory and its own database.
3 14-digit barcodes. Synthetic GTINs were one digit too long for an EAN-13. Stage 06 rejected every barcode as unparseable while stage 04 scored the same strings as perfect matches. Proper 12-digit body plus computed check digit, with a per-dataset prefix.
4 Run collision. Both modes wrote the same filenames. The benchmark run overwrote the synthetic run, so the dashboard's artwork tab lost its images. Per-mode output directories; the artwork tab works again.
5 Absent treated as contradictory. A missing barcode scored 0.0 — numerically identical to three barcodes that disagree. Every one of 1,092 rows was rejected, including the 958 matched correctly. A router emitting one constant label is not routing. Confidence is a weighted mean over observable signals; missing evidence caps confidence instead of faking negative evidence.
Why this matters more than the pipeline itself. A leak does not announce itself. Accuracy went up, the tests stayed green, and the dashboard looked healthier. The only thing that caught it was refusing to accept a number that was too clean for the problem — 100% on a 1,081-product catalog, when an independent code path scored the same engine at 85.1%. Two measurements of the same thing disagreeing is the signal; everything else followed from pulling that thread.

Honest Findings

What Works

  • Text matching at scale: 87.7% / 80.2% top-1 on two real e-commerce benchmarks, 95% top-3 recall on both
  • Signal independence: Four unrelated signals (text/phonetic/semantic/barcode) stay uncorrelated
  • Routing decisions: 0% incorrect auto-merges on real data; confidence thresholds are predictive
  • Learning loop: Human-approved aliases boost confidence 10% on re-submission
  • Graceful degradation: Missing one signal (barcode) doesn't crash—reverts to 0.35 confidence

What Doesn't Work (and Why)

  • Text alone cannot auto-merge at scale: Weighted score is 0.35 × text_match, max 0.35 (below 0.60 hold threshold). Needs barcode or packaging agreement.
  • OCR on real images (expected): Synthetic renders give 95% accuracy; real photos drop to 70–80% (reflections, angles, foreign text)
  • Phonetic matching on non-English brands: Metaphone designed for English; degrades on Asian/European brands
  • Stage 05 rarely triggers: On 30-product synthetic catalog, retrieval is almost always decisive; ambiguity is rare (0/20 events)

Key Design Decision That Prevented Major Bug

Initial approach: Made ANY artwork/supplier disagreement a hard veto (blocks auto-merge). Result: 100% held for review (useless).

Correction: Only identity-field (barcode) conflicts block auto-merge. Cosmetic disagreements (brand abbreviation) are weighted signals, not blockers. This distinction matters because synthetic feed corrupts 100% of rows.

Lesson: Guardrails should fail closed (hold, not reject) and should distinguish problem severity (cosmetic vs identity-level).
